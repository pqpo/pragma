# ADR 049: 知识库只保存当前状态

## 状态

Accepted

## 背景

Pragma Desktop 是 local-first 的用户端应用。早期 Context Store 在每次正式写入时保存完整快照和修订记录，
同时产品还提供草稿、审批、rebase 和 Bundle 导入流程。这把并发安全、变更工作流和长期版本管理混成了一个
系统，并导致知识库占用随编辑次数持续增长。

用户真正需要的是可靠的当前内容、可控的 Agent 修改流程，以及显式备份。长期历史更适合由用户导出的
`.pragma` 文件和 Git 等通用工具管理。

## 决策

托管知识库只持久化当前 Markdown 文件、元数据和内容 `snapshotHash`，不再保存数字内容版本、历史快照或
修订记录。所有正式写入使用旧 `snapshotHash` 作为 CAS 条件，并通过稳定 journal、暂存目录和原子目录替换
保证崩溃恢复与并发安全。

Agent 更新仍使用稀疏草稿、人工审批和显式 rebase，但这些是工作流，不是版本库。活动草稿内嵌其基线快照，
避免正式知识库存储历史副本；合并或拒绝后将整个草稿移入回收站，任务记录只保留请求、状态和时间。拒绝任务
重试时从当前知识库创建新草稿。

知识库导出是用户可见的备份边界。导出前编辑器必须先保存待落盘修改；Bundle 只包含当前快照。导入更新
以 snapshot hash CAS 替换当前内容，相同内容为 no-op。需要历史的用户可将定期导出的 `.pragma` 文件纳入 Git。

Context Store v4 首次访问时迁移到 v5：先为活动旧草稿保留其精确基线，再备份 v4 manifest，写入稳定迁移
journal，发布 v5 manifest，最后把 `revisions/` 移入系统回收站。迁移可重放，失败保留原数据。Bundle 安装
状态通过相邻 v5→v6 迁移删除已废弃的 `baseRevision`，保留 snapshot hash。

## 后果

- 知识库磁盘占用由当前内容和活动草稿决定，不再随正式编辑次数单调增长。
- Desktop 不提供浏览或恢复知识库历史版本的产品能力。
- 冲突检测依赖内容哈希，不依赖数字版本号。
- 用户自行决定备份频率、Git 仓库布局和保留策略。
- 旧历史迁移后可从系统回收站恢复，但不会再被 Pragma 读取。
