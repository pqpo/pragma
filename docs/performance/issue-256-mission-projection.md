# Issue #256 Mission 投影构建性能记录

## 结论

Issue #256 指出的主进程同步风险可以在旧实现中直接确认：写入首次 `await` 前会校验全部条目、对全部条目
执行截断和二次 Schema 校验，然后才应用 1,000 条/4 MiB 的输出上限；文本截断还会用 `Array.from()` 为
完整字符串创建字符数组。这里是 Electron 主进程的投影构建路径，不是 Renderer 每次按键或每个 Token
必经的路径，因此本次结果不把它表述为输入偶发卡顿的唯一根因。

修复采用主进程时间分片，而不是 Worker：

- 构建开始前先让出一次事件循环，之后以 4 ms 为同步工作预算执行完整输入校验。
- 所有输入仍逐条通过 `MissionChatEntrySchema`；只有最终可能保留的最近 1,000 条进入截断和 JSON 编码。
- v1 迁移只校验旧格式 envelope，条目交给同一时间分片校验器一次完成校验、构建和返回，不再先整数组同步校验后由写入器重复校验。
- Unicode 截断按 code point 流式计数并按 UTF-16 边界切片，不再创建完整字符数组；扫描长文本期间也按预算让出。
- 条目 JSONL 只序列化一次，编码结果同时用于精确字节预算与文件写入。
- 同一路径写入按调用顺序串行化，避免较早的大投影晚完成后覆盖较新的投影；失败不会阻塞后续写入。
- 临时文件、`sync()`、`close()`、原子 `rename()` 与失败清理保持不变；旧格式只在完整校验成功后、写入新文件前占用备份路径，失败重试不会保留无效备份。

未选择 Worker 是有意的：投影输入本身可能达到数十 MiB，结构化克隆会增加传输时间和峰值内存，还需要
维护常驻 Worker 的生命周期和有界队列。时间分片保留单份输入，并直接限制主进程连续占用时间。

## 可重复基准

运行：

```bash
pnpm --filter @pragma/desktop benchmark:mission-projection
```

脚本使用实际 `mission-execution-projection.ts`，分别构造短 ASCII、多条多字节、长多字节和需要 Unicode
截断的输入。它报告完整校验、候选截断/编码、同步 CPU、最大连续同步切片、让出次数、文件写入、总耗时、
事件循环最大相邻 turn 间隔，以及 RSS/Heap 峰值。该策略没有 Worker/进程传输，因此输出明确将
`transferMs` 记为 `null`，而不是把它混入构建时间。

以下结果来自 2026-09-18 的 Intel Core i7-9750H、16 GiB、macOS 25.6、Node 24.18.0，单场景一次受控运行：

4 ms 是检查点预算，不是抢占式调度保证。一次不可中断的 Zod/JSON 操作或计时器调度会产生少量超调；本机
最重场景的最大连续同步切片为 7.921 ms，且 40 MiB 输入不再形成一个覆盖完整构建过程的同步长任务。
短输入的 JIT/首次 Schema 解析也会影响单次结果，因此脚本保留原始数值，不宣称微秒级稳定性。

## 正确性与回归边界

- 中文、emoji/代理对、无需截断、恰好到边界与超出边界都按 Unicode code point 语义验证。
- 即使无效条目位于最终会省略的旧历史中，完整输入校验仍拒绝写入，并保留已有投影。
- 条目数、4 MiB 字节预算、最新条目顺序、`omittedEntries` 与 `truncatedFields` 沿用原语义。
- 同一路径并发写入验证最终内容来自后调用；写入完成后可以立即读取。
- v1 迁移验证完整返回旧数据、落盘仍受既有上限约束，且省略范围内的无效条目仍会阻止迁移。
- v1 首次校验失败不会创建备份；修复源文件后重试会备份修复后的有效内容，再删除旧源文件。
- 原子 `rename()` 失败会关闭句柄并删除临时文件，不会留下半份投影。
- 现有 Mission Store 回归继续覆盖 JSONL 读取、逆向分页、损坏尾部、字节截断、旧 JSON 迁移和备份。

基准测量的是主进程投影构建与持久化，不等价于端到端输入延迟，也不替代 Renderer 的 #254/#255 基准。
