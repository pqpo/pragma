# Issue #255 Mission 流式更新基准

## 结论

Issue #255 描述的三个线性热点在 `main@827c20ed` 上均可确认：

1. 首 Token 解析会在每条正文更新上执行 `entries.find()`。
2. 每个有效帧批次都会复制完整 `entries` 并重建 ID 索引。
3. 发布变化条目时会再次 `filter()` 完整 `entries`。

修复后，纯 `content` append 使用现有 `MissionLiveEntryStore` 的 ID 索引读取当前条目，批处理直接返回
`changedEntries`。有序快照只在插入、移动、刷新、分页、状态合并或 Mission 切换等结构边界物化。结构边界
会先吸收已发布的流式正文，因此延迟物化不会回滚或丢失内容。

## 可重复基准

运行：

```bash
pnpm --filter @pragma/desktop benchmark:mission-stream
pnpm --filter @pragma/desktop benchmark:mission-stream-ui
```

脚本使用实际 `mission-conversation-model.ts`，对 100、1,000、5,000 条已加载消息分别执行 50 次预热和
1,000 次单条正文追加。`materialized` 模拟修复前的全量快照及发布扫描，`incremental` 使用生产代码的新
增量选项。以下结果来自 2026-09-18 的 Intel Core i7-9750H、16 GiB、macOS 25.6、Node 24.18.0：

| 消息数 | 路径         | 批处理 p50 / p95 (ms) | 发布 p50 / p95 (ms) | 全量索引构建 | 有序数组复制 |
| -----: | ------------ | --------------------: | ------------------: | -----------: | -----------: |
|    100 | materialized |       0.0069 / 0.0178 |     0.0024 / 0.0031 |        1,050 |        1,050 |
|    100 | incremental  |       0.0014 / 0.0015 |     0.0002 / 0.0002 |            0 |            1 |
|  1,000 | materialized |       0.0577 / 0.0977 |     0.0132 / 0.0155 |        1,050 |        1,050 |
|  1,000 | incremental  |       0.0009 / 0.0011 |     0.0002 / 0.0002 |            0 |            1 |
|  5,000 | materialized |       0.4422 / 0.7339 |     0.1006 / 0.1043 |        1,050 |        1,050 |
|  5,000 | incremental  |       0.0008 / 0.0009 |     0.0001 / 0.0001 |            0 |            1 |

最后一列中的增量路径 `1` 是基准结束时为一致性校验执行的一次结构物化；1,050 次正文追加本身没有复制
有序数组，也没有重建全量索引。

首 Token 查询对照：

| 消息数 | 全表扫描 p50 / p95 (ms) | ID 索引 p50 / p95 (ms) |
| -----: | ----------------------: | ---------------------: |
|    100 |         0.0015 / 0.0018 |        0.0001 / 0.0001 |
|  1,000 |         0.0134 / 0.0139 |        0.0001 / 0.0001 |
|  5,000 |         0.0338 / 0.0342 |        0.0001 / 0.0001 |

在此固定变化条目数的对照中，增量批处理 p95 不随已加载消息量增长，因此不需要再增加 rAF、延迟刷新或
时间分片。rAF 仍只负责把同一帧的 IPC 更新合批。

## 生产 Electron 输入对照

`benchmark:mission-stream-ui` 使用 production React bundle、实际 `MissionChatComposer`、
`MissionChatEntryView`、Markdown 渲染与 `MissionLiveEntryStore`，在 Electron 43.2.0 中比较静止长会话与
每帧持续追加输出。每个场景执行 40 次固定长度输入并等待双 rAF 绘制；持续输出场景期间完成并在 DOM 中
观测到 80 次增量追加：

| 消息数 | 场景     | 输入到绘制 p50 / p95 (ms) | Long Task 数量 / 总时长 | JS Heap 变化 (MiB) |
| -----: | -------- | ------------------------: | ----------------------: | -----------------: |
|    100 | 静止     |             33.30 / 35.20 |                0 / 0 ms |             -7.141 |
|    100 | 持续输出 |             33.30 / 35.30 |                0 / 0 ms |              2.211 |
|  1,000 | 静止     |             33.40 / 34.90 |                0 / 0 ms |              1.522 |
|  1,000 | 持续输出 |             33.40 / 35.10 |                0 / 0 ms |             -3.894 |
|  5,000 | 静止     |             33.30 / 34.90 |                0 / 0 ms |              1.422 |
|  5,000 | 持续输出 |             33.30 / 34.70 |                0 / 0 ms |             -2.615 |

5,000 条消息时持续输出相对同规模静止场景的输入 p95 没有增加，也没有产生 Long Task。Heap 单次差值受
GC 时机影响，因此保留原始场景值，不把负数或小幅波动解释为稳定内存收益。基准 runner 会拒绝 renderer
错误、缺失场景、样本不足、没有真实 DOM 输出变化，以及未贯穿全部 40 个输入样本的流式活动，避免把失败
或中途停止的执行误报为成功数据。

## 正确性覆盖

- 连续、重复、旧 revision、缺口、invalidate 与刷新重放沿用现有确定性测试。
- 新增 5,000 条消息下的纯 append 引用稳定、结构边界物化、插入顺序与正文保留测试。
- 新增多 execution 首 Token 解析，覆盖同一更新中多个成员、尚未进入快照的条目，以及高 revision 的
  upsert 先于低 revision append 到达时的归属隔离。
- 共享缓存只保存完整物化快照；延迟正文留在 hook 私有状态，在刷新、分页、状态合并与 Mission 切换边界
  从 live store 物化后再写入缓存。
- 未读输出的纯 append 快速路径不再预先构建完整 entry Map。
- live store 的轻量发布订阅继续驱动跟随最新消息，不需要为每个 Token 重渲染整个 Mission 页面。
- 首次页面读取前到达的更新会在刷新合并消费前，基于最近的前置 revision 重放首 Token 归属。
- Mission 页面回归覆盖缓存恢复、历史 prepend、upsert 移动、短文本/分歧重写和流式订阅。

模型微基准隔离 Issue #255 指定的同步数据处理成本，不把 `mission.stream_flush` 当成端到端输入延迟；
Electron 对照独立记录输入到绘制、Long Task 和 Heap。两者都不冒充用户现场火焰图。Composer 自身的隔离
基准继续由 `benchmark:composer` 与 `docs/performance/issue-254-mission-composer.md` 记录。
